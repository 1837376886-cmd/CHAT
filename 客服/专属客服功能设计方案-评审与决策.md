## 第一部分：产品经理评审结果

### P0（严重，必须解决）

#### P0-1：通知机制 v1 存在"欺骗用户"的法律与品牌风险
- **问题描述**：v1 实现中 `NotifyService` 仅打印日志，但前端 UI 固定显示"已发送短信通知您的专属客服"。文档明确说这是"已知差距"，并在风险表中承认"业务方误以为已发送"。
- **业务影响**：用户看到"已发送短信"后，若客服迟迟不上线，用户可能投诉"短信未收到"或质疑平台诚信。在强监管行业（金融、医疗）可能构成虚假宣传，引发客诉甚至监管风险。
- **建议方案**：前端文案改为真实状态，如"您的专属客服当前离线，上线后将第一时间为您服务"。若业务方坚持要"已发送通知"的体感，至少改为"已通知您的专属客服"（不指定渠道），并确保 v2 尽快接入真实通知通道。

#### P0-2：专属客服离线时"只能等待"无兜底，业务连续性断裂
- **问题描述**：文档明确"专属客服不在线时...将会话挂起等待客服上线"。没有任何代班、升级、或智能客服兜底机制。风险表中也承认"专属客服永久离职导致访客永远等不到"。
- **业务影响**：若专属客服请假、离职、或临时断网，用户发起咨询后陷入无限等待，体验极差，可能导致高价值用户流失。对于 B2B 或高客单价业务，这是不可接受的。
- **建议方案**：v1 至少增加一个"离线超时转公共客服池"的兜底策略。例如：专属客服离线超过 15 分钟，自动将用户转入"临时会话"池，由其他在线客服接待，并给用户提示"您的专属客服暂时离线，已为您安排其他客服"。同时记录该转接，专属客服上线后可查看离线期间的会话记录。

#### P0-3：转接完全禁止，与"临时有事需代班"的现实冲突
- **问题描述**：决策结论第 9 条"专属会话转接：禁止（避免破坏专属语义）"。前端工作台对专属会话隐藏转接按钮。
- **业务影响**：专属客服临时开会、身体不适、或系统故障时，没有任何机制让同事代班。这与真实客服排班场景严重冲突，可能导致用户问题无人处理。
- **建议方案**：允许"强制转接"或"代班"机制，但需满足：
  1. 仅允许转给同组/同权限客服；
  2. 转接后原专属绑定关系不变（下次该用户来访仍优先找原专属客服）；
  3. 转接记录留痕，供管理追溯。
  或者至少允许管理员/班长在后台强制"解除专属绑定"（临时降级为匿名访客流程）。

### P1（重要，强烈建议解决）

#### P1-1：多端独立会话 + 好友式工作台存在体验矛盾
- **问题描述**：决策结论第 4 条"多端各自独立：每次打开新建 cs_session"，但第 10 条前端工作台要求"左侧分'我的客户'（按用户聚合）"。文档风险表最后一行也承认"多端各自独立，客服看到同一用户多个条目"，并说"v1 接受此体验；v2 前端合并展示"。
- **业务影响**：v1 中客服侧按用户聚合显示，但底层是多端独立 session。这会导致：
  - 同一用户在 APP 和 PC 分别发消息，客服在"我的客户"列表里只看到一个条目，但点进去后消息来源混杂（deviceType 标签区分），客服可能困惑；
  - 消息已读状态难以管理（A 端已读不代表 B 端已读）；
  - 历史消息查询是按 `cs_user_id + external_user_id` 聚合，与"独立 session"的设计目标冲突。
- **建议方案**：要么 v1 就统一按用户聚合（底层 session 也按用户维度管理，多端共享同一个 active session），要么前端 v1 就按 session 分开展示（与底层一致），不要"底层独立、前端聚合"的半吊子方案。推荐前者：专属客服场景下，一个用户对应一个客服，多端消息应合并为同一会话。

#### P1-2：用户侧 v1 不显示历史消息，专属场景下体验不完整
- **问题描述**：决策结论第 11 条"v1 仅客服侧可查（用户侧 v2 再补）"。前端访客 SDK 部分也明确"v1 用户侧不加载历史消息"。
- **业务影响**：专属客服场景通常涉及长期服务关系（如理财顾问、客户经理）。用户换设备或重新打开窗口后看不到之前的对话记录，无法上下文衔接，严重影响专属服务的连续性。这与"专属客服"强调的"长期一对一关系"定位矛盾。
- **建议方案**：v1 至少提供"打开即加载该用户与专属客服的全部历史消息"的基础能力。技术上已有 `/cs/messages/history` API，只需前端在用户接入时调用并渲染。不应推迟到 v2。

#### P1-3："拒绝服务"（bound_cs_user_id 为空/失效时）过于粗暴
- **问题描述**：决策结论第 7 条：专属客服失效时"拒绝服务"，提示"请联系您的业务联系人重新分配专属客服"。
- **业务影响**：用户有问题需要咨询，却被系统直接拒绝，且没有任何自助或降级路径。这会导致用户投诉量激增，尤其当外部系统数据同步延迟或配置错误时，大量用户会被误伤。
- **建议方案**：拒绝服务时，至少将用户降级为"匿名访客"流程，由公共客服池接待，同时给用户提示"您的专属客服配置异常，已为您安排其他客服，请联系业务方确认专属客服信息"。这样既解决问题，又保留业务方的整改空间。

#### P1-4：客服侧"我的客户"列表包含大量离线用户，造成干扰
- **问题描述**：前端工作台设计（6.2 节）中，"我的客户"列表包含"离线用户灰色显示，仍保留在列表中"，按 `last_msg_time` 倒序排列。
- **业务影响**：若客服服务了大量用户，列表会被长期不活跃的离线用户占满，活跃客户被淹没。客服需要频繁滚动查找，效率低下。
- **建议方案**：增加筛选/折叠机制：
  - 默认只显示"在线"或"今日有消息"的用户；
  - 离线超过 7 天的用户自动折叠到"历史客户"子分组；
  - 提供搜索框按用户名/ID 过滤。

### P2（一般，可优化）

#### P2-1：登录用户不计入 activeCount，可能导致客服实际负载不可见
- **问题描述**：决策结论第 5 条"接待名额仅约束匿名访客，登录用户会话不计入 activeCount"。
- **业务影响**：一个客服可能同时处理 5 个匿名访客 + 20 个专属客户，系统却显示"当前接待 5/5"，管理层无法评估真实 workload。客服本人也可能因专属客户过多而响应延迟。
- **建议方案**：`activeCount` 可拆分为"匿名 activeCount"和"专属 activeCount"，或至少在后端监控/管理后台中统计专属会话数，供运营分析。v1 可仅做后台统计，不强制限流。

### 亮点

#### 亮点：token + 身份一致性校验设计周全
- **位置**：5.2 节 `resolveVisitor` 的三条安全规则。
- **说明**：方案充分考虑了"同一设备换账号"（A 用户用过 t1，B 用户在同一设备登录也带 t1）和"退出登录后残留身份"的串号风险，通过强制生成新 token 创建新 visitor 记录来隔离。这在多端、多账号场景下是严谨的安全设计，值得保留。

## 第二部分：测试工程师评审结果

### Critical（上线前必须修复）

#### Critical-1：多端广播映射并发安全与断连可靠性
- **问题描述**：方案新增 `Map<String, Set<Channel>> userChannels`（key = `csUserId:externalUserId`），客服回复时广播到该用户所有端。`registerUserChannel` / `unregisterUserChannel` 在 Netty I/O 线程执行，但 `broadcastToUser` 可能在业务线程（如 HTTP 线程）执行。
- **当前代码薄弱环节**：现有 `ChatChannelHandler` 和 `WebSocketHandler` 各自维护独立的 `visitorChannels` / `connectionManager.visitorSessions`，都是**单 Channel 映射**。方案新增的 `userChannels` 需要**多 Channel 集合**，但 `unregisterUserChannel` 存在竞态（`isEmpty()` 判断和 `remove(key)` 非原子）。
- **预期 Bug 表现**：用户多端在线时，某端断开，其他端收不到客服广播消息。或断开端 channel 未从 Set 中移除，后续广播时向已关闭 channel 写数据，触发 Netty `ClosedChannelException`。
- **建议测试用例**：
  1. 用户同时打开 APP 和 PC 两端，客服发送消息，两端都收到。
  2. 在 100 并发下，随机断开一端，检查 `userChannels` 中是否残留失效 channel。
  3. 使用 Netty 的 EmbeddedChannel 做单元测试，模拟 `channelInactive` 和 `broadcastToUser` 并发执行。

#### Critical-2：重复分配：processPendingOnCsOnline 与 connect 请求并发
- **问题描述**：`processPendingOnCsOnline` 消费挂起队列时，如果同时有新 `connect` 请求进入，是否会出现重复分配？
- **当前代码分析**：`processPendingOnCsOnline` 无分布式锁。`tryConsumeWaitingAfterClose` 有锁（`cs:allocate:lock:{csUserId}`），但 `processPendingOnCsOnline` 没有。
- **并发场景**：客服 A 上线执行 `processPendingOnCsOnline`，同时访客 V 调用 `/cs/connect`。双方同时 `createSessionAndAssign` → 访客 V 被分配了两个 session，客服 A 的 activeCount 被加了两次。
- **预期 Bug 表现**：同一访客出现多个 ACTIVE session；客服 activeCount 虚高；访客收到多条欢迎语。
- **建议测试用例**：构造 pending 状态后，同时触发客服上线和访客 connect，验证最终只有 1 条 ACTIVE 记录。

#### Critical-3：客服回复广播时某端断开导致消息丢失
- **问题描述**：方案中 `broadcastToUser` 的 `writeAndFlush` 是异步的，`isActive()` 瞬间为 true，但写入过程中 channel 可能关闭。Netty 的 `writeAndFlush` 失败不会抛异常到调用方（而是设置 future 为失败），代码中没有监听 `ChannelFuture`。
- **预期 Bug 表现**：用户某端在客服发送消息的瞬间断网，该消息对该端永久丢失（用户侧无历史消息加载，v1 不开放）。
- **建议测试用例**：用户多端在线，在 `broadcastToUser` 遍历到第二个 channel 时强制关闭该 channel，验证第一个 channel 收到消息，第二个未收到，且数据库中该消息已保存。

### High（强烈建议修复）

#### High-4：换人检测逻辑边界绕过
- **问题描述**：`resolveVisitor` 中 token + externalUserId 一致性校验有三条规则，但存在边界漏洞。
- **遗漏场景**：token 关联过登录用户 A，现在未传 externalUserId（用户 A 退出登录后，前端仍带旧 token）。代码会走到最后的 `return visitor;` —— 匿名访客复用了登录用户的 token 和 visitor 记录！
- **预期 Bug 表现**：用户退出登录后，同一设备继续浏览，聊天记录仍关联到原登录用户；或客服侧看到"匿名访客"却有 externalUserId。
- **建议测试用例**：
  | 步骤 | 操作 | 预期结果 |
  |---|---|---|
  | 1 | 用户 A 登录，connect 带 externalUserId=A, token=t1 | 创建 visitor，external_user_id=A |
  | 2 | 用户 A 退出登录，connect 带 token=t1，未传 externalUserId | **应生成新 token t2**，创建匿名 visitor |
  | 3 | 用户 B 登录，connect 带 externalUserId=B, token=t1 | 检测到不一致，生成新 token t3，创建 visitor B |

#### High-5：cs_message 冗余字段回填失败
- **问题描述**：方案要求 `cs_message` 新增 `cs_user_id` 和 `external_user_id`，写入时回填。当前 `CsMessageServiceImpl.sendMessage` 完全没有回填逻辑。如果改造时只改 DDL 和实体类，但 `sendMessage` 接口未增加参数或内部未查询 session 信息回填，则所有消息的冗余字段为 NULL。
- **预期 Bug 表现**：`cs_message` 表中 `cs_user_id` / `external_user_id` 大量为 NULL，导致 `/cs/messages/history` 按这两个字段查询时漏数据。
- **建议测试用例**：验证所有写入路径（WebSocket 消息、HTTP 发送消息、系统消息、转接消息）都正确回填。

#### High-6：登录用户每次打开新建 session，表膨胀与查询性能
- **问题描述**：方案决策 #4："登录用户每次打开都新建 session"，且 "不占 max_sessions"。`cs_session` 表增长 = 登录用户数 × 打开次数。`cs_session` 无自动清理机制（方案提到"可后续加定时清理任务"）。
- **预期 Bug 表现**：`cs_session` 表在高峰时段快速增长；`selectActiveSessionsByCsUserId` 查询数据量增大。
- **建议测试用例**：同一 externalUserId 并发 10 次 connect，验证创建 10 条 session 记录。压测 1000 用户 × 每人 10 端，观察插入性能和查询延迟。

#### High-7：Redis 限流键丢失导致通知风暴
- **问题描述**：`LoggingNotifyService` 使用 Redis SETNX 限流。Redis 重启或 key 过期后，限流状态丢失。如果客服长期离线，同一访客每次 connect 都会触发通知。
- **预期 Bug 表现**：Redis 重启后，大量 pending 访客同时触发通知，日志暴增，后续接入真实短信接口时产生费用风暴。
- **建议测试用例**：设置 notify_min_interval_sec = 600，访客 V 触发一次通知。在 600 秒内重启 Redis。访客 V 再次 connect，验证是否再次触发通知（预期会触发，这是已知风险）。

### Medium

#### Medium-8：getOrCreateVisitor 不走 IP+UA 兜底后，匿名访客换浏览器识别
- **问题描述**：方案要求"登录用户不走 IP+UA 兜底"，但匿名访客仍走现有逻辑。登录用户换浏览器后，由于严格按 token 匹配，会生成新 visitor 记录。这是符合预期的（多端独立会话）。
- **真正的风险**：如果前端在登录用户模式下，清除了 localStorage 中的 token（或用户换设备），用户会生成新 visitor，但 `external_user_id` 相同。客服侧"好友式分组"需要按 `external_user_id` 聚合，而不是 `visitor_id`。
- **预期 Bug 表现**：客服工作台"我的客户"列表中，同一用户出现多个条目（v1 接受此体验，但需确认前端聚合逻辑）。

#### Medium-9：客服身份迁移到 cs_config 后的数据不一致
- **问题描述**：方案第 1 期将客服身份从 `sys_user.is_customer_service` 迁移到 `cs_config.status`。
- **风险**：`WebSocketHandler.handleAuthMessage` 中仍可能按 `sys_user.is_customer_service` 判断，导致禁用客服自动上线。
- **预期 Bug 表现**：客服在 `cs_config` 中已被禁用，但 WebSocket 认证时仍按 `sys_user.is_customer_service` 判断，导致禁用客服自动上线。

#### Medium-10：转接接口未拦截专属会话
- **问题描述**：方案要求"专属会话禁止转接"，但当前 `CustomerServiceController.requestTransfer` 中没有对 `visitor.external_user_id` 的校验。
- **预期 Bug 表现**：专属会话被成功转接，破坏一对一绑定语义。

#### Medium-11：processPendingOnCsOnline 容量检查与登录用户不计入 activeCount 的冲突
- **问题描述**：`processPendingOnCsOnline` 检查 `active < max`，但登录用户的 session **不计入** `activeCount`。
- **并发场景**：客服 A 的 max=5，当前 activeCount=5（5 个匿名访客）。专属访客 V 进入，客服 A 离线，V 被挂起到 pending。客服 A 上线，`active=5 >= max=5`，不会处理 V。
- **预期 Bug 表现**：专属访客被挂起，即使客服上线后仍有"容量"接待专属访客（因为专属不占名额），但 `processPendingOnCsOnline` 的容量检查会阻止分配 —— 这是 Bug。

### 当前代码中已有的薄弱环节（与方案叠加后风险放大）

| 薄弱环节 | 位置 | 与方案叠加后的风险 |
|---|---|---|
| `ChatChannelHandler` 和 `WebSocketHandler` 并存，维护两套独立的 Channel 映射 | `ChatChannelHandler.java`, `WebSocketHandler.java` | 方案新增 `userChannels` 广播映射，需要确定注入到哪个 Handler。如果两套都改，逻辑重复；如果只改一套，另一套的推送逻辑会遗漏广播。 |
| `ConnectionManager` 的 `visitorSessions` 是 token -> UserSession **一对一** | `ConnectionManager.java:45` | 方案要求一个 externalUserId 对应多 Channel，但 `ConnectionManager` 不支持。改造时需要重构为 token -> Set<UserSession> 或新增独立映射。 |
| `sendMessageToVisitor` 只发单端 | `ChatChannelHandler.java:64`, `ConnectionManager.java:248` | 方案要求客服回复广播到用户所有端，所有调用 `sendMessageToVisitor` 的地方需要改为 `broadcastToUser`。遗漏任何一处都会导致某些场景下广播失效。 |
| `CsMessageService.sendMessage` 接口参数不足 | `ICsMessageService.java:18` | 方案要求回填 `cs_user_id` / `external_user_id`，但现有接口只有 `sessionId, fromType, fromUserId, content`。需要改接口签名，或内部查 session 表回填。所有调用点都需要验证。 |
| `getOrCreateDefault` 隐式创建客服记录 | `CustomerServiceController.java:206` | 方案要求"只读不创建"，但 `csOnline` 中仍调用 `csConfigService.getOrCreateDefault`。如果非客服调用 `/cs/online`（虽然前面有 `is_customer_service` 校验，但改造后校验逻辑会变），可能意外创建记录。 |
| `processPendingOnCsOnline` 无分布式锁 | `CustomerServiceAllocationService.java:269` | 与 `connect` 并发时重复分配，已在 Critical #2 中详述。 |
| 客服下线/心跳超时关闭会话后，对专属访客的处理 | `CsHeartbeatCheckTask.java:98` | 当前代码对所有会话都 `closeSession` + `tryConsumeWaitingAfterClose`。方案要求"专属客户的 session 不重新分配，挂起 + 通知"。需要改造 `handleCsTimeout`，区分专属会话和匿名会话。 |

## 第四部分：关键取舍说明

### 取舍 1：产品经理建议"统一按用户聚合" vs 测试指出"Netty 大改成本高"
- **决策**：v1 保持"底层独立 session + 前端按用户聚合"的当前设计
- **理由**：这是合理的分层架构，不是半吊子。底层独立保证数据清晰（每端有 deviceType、独立 session 日志），前端聚合保证客服体验。统一聚合需要把 `ConnectionManager` 从一对一改多对多，涉及 Netty 核心链路，v1 风险太高

### 取舍 2：产品经理建议"离线超时转公共客服池" vs 实现成本
- **决策**：v1 不做自动转接，改为前端「找其他客服」按钮主动降级
- **理由**：自动转接需要改 `allocate()` 核心逻辑 + 前端状态机，成本高。一个按钮让用户主动选择降级，既解决兜底问题，又不侵入分配核心

### 取舍 3：测试 Critical-3"广播消息丢失" vs v1 用户侧不加载历史
- **决策**：v1 加 `ChannelFuture` 监听记录日志，但不加消息补偿
- **理由**：消息补偿需要持久化未送达消息 + 重推机制，成本高。v1 先记录失败日志，v2 接入用户侧历史加载后，消息丢失问题自然缓解（用户刷新可见）
